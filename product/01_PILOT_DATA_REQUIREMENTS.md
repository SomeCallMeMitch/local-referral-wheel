# Pilot data requirements
Do not build software. This is a minimal record specification for a future manual pilot.

| Must track manually | Practical existing tool | Access / retention |
|---|---|---|
| Provider profile, scope, geography, capacity, response owner | Form + controlled member directory | Member-visible business details only |
| Consent and named intended recipient | Private form/email record | Sender/recipient/coordinator only |
| Referral ID, relationship ID, event, source/recipient, dates/status/next action | Restricted spreadsheet or simple CRM | Customer data not in public member directory |
| One action, owner, due date, result | Meeting notes + small action list | Participants; sensitive details removed |
| Dues/payment dates, cancellation/renewal | Billing record + payment receipt | Operator/member |
| Private optional outcomes and evidence tier | Private per-member report | Separate permissions from group view |
| Operator hours by task | Time log | Operator |
| E only: covered relationship, agreed fee rules, job IDs, cash basis, invoices, credits and disputes | Restricted fee ledger | Fee parties/operator only |
| C only: baseline/cohort/action/results and support time | Small experiment log | Participating firm and facilitator |

A form submission is not automatically consent for every use. Collect only necessary information. Don't upload bank records/customer lists to an AI system for convenience.

## Minimum fields and definitions
Provider ID can be a simple code. A referral references two providers and one customer event. A job/payment links to the referral without duplicating its value. Fee records link to the job and agreement. A relationship ID supports the founder's ongoing coordination model without assuming every relationship-derived deal is fee-eligible.

Do not demand monthly total revenue, employee counts, margins or marketing spend merely because the original blueprint listed them. A dues-only network can function with status records and optional value disclosure. E cannot credibly invoice percentages while treating the fee basis as optional; choose a different pricing model if recipients reject verification.

## Manual report example
Member 04, reporting month 2. Dues $199. Three accepted referrals received, two sent. One signed job not yet paid; two awaiting decision. Collected referred revenue: not provided. One follow-up exercise completed. One commitment due/completed. Causal ROI: not established. Next action: recipient to update open quote Friday.

This is less dramatic than a large revenue badge and more useful than an inflated total.

## Boundaries
Permissions are needed even in spreadsheets. Store customer contacts separately from the shared directory. Use proposed retention policy in referral-system/01, adjusted for applicable legal/accounting requirements. Maintain correction dates and who supplied each outcome.
